How they link together

Each metric reuses the same comparison and asks one more thing.

  1. Count
    Precision divides the relevant chunks found by the {{ k }} slots. Is what we return clean?
  2. Count
    Recall divides the same relevant count by all relevant chunks in the ground truth. Did we miss anything?
  3. Combine
    F1 joins Precision and Recall into one number that is only high when both are.
  4. Yes / no
    Hit Rate keeps one question per query: was the relevant count at least 1? It is the yes/no version of Recall.
  5. + position
    MRR adds where: for a hit, how high is the first relevant chunk?
  6. + all positions + grades
    NDCG adds where every relevant chunk is, and how relevant it is.

4. How do we fix this problem?

Possible problems and what to check
Possible problemWhat to check
Document missingIs the source document uploaded to the knowledge base?
Parsing failureWas the text extracted correctly from the PDF or web page?
Chunking issueIs the answer split across chunks, or cut in the middle?
Embedding issueDoes vector search find chunks with the same meaning?
Query issueDoes the question use different words from the document?
Retrieval issueIs hybrid search (keyword + vector) working?
Ranking issueDoes the reranker put the relevant chunks first?
Very important interview point

Retrieval evaluation must find failure, not hide it. If all retrieved chunks are irrelevant, Precision, Recall, F1, Hit Rate, MRR and NDCG must all be zero. The generation layer should also have a relevance or confidence check, so it does not answer from irrelevant context.

6. Important production-level rule

Never let the LLM answer blindly from irrelevant retrieved chunks. Before generation, check whether the retrieved context is relevant:

  • Relevant context found → generate the answer.
  • No relevant context found → return “I couldn't find this information in the available documents.”
  • Low-confidence retrieval → retry the search, or ask the user to clarify.

Remember this troubleshooting order

  1. Document
  2. Parsing
  3. Chunking
  4. Embedding
  5. Indexing
  6. Query
  7. Retrieval
  8. Reranking
  9. Evaluation

Follow this order when you debug a failed RAG retrieval.

What problem this evaluation solves

  • Separates retrieval from generation. A wrong chatbot answer can come from the retriever (wrong chunks) or from the LLM. These scores test the retriever alone, so you know where to fix.
  • Replaces guessing with numbers. Changing chunk size, embeddings, K or adding a reranker becomes a measured experiment, not a feeling.
  • Finds the exact failing questions. Each query has its own scores, so you see which questions break and why.
  • Catches regressions before users do. Compare a new retriever with the current one, and fail the build if a metric drops.
